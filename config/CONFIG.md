# 配置表说明

所有配置表位于 `config/json_output/`，由 `config/xlsx/` 中的 Excel 文件通过 `config/xlsx_to_json.py` 生成。

## 1. items.json — 物品表

### ItemType 枚举

| 值 | 含义 | 说明 |
|----|------|------|
| 0 | REGULAR | 常规合并物品 |
| 1 | LAUNCHER | 发射器，双击生成物品 |
| 2 | CRAFTING | 制作台，拖入材料合成 |
| 4 | RECIPE_PRODUCT | 制作产物（丹药、阵法、飞剑等） |
| 5 | EFFECT | 效果道具（剑气、回复药等） |

### 通用字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | int | 唯一标识 |
| `name` | string | 物品名称 |
| `level` | int | 等级，同 group_id 内升级；`type=4` 配方产物取所需材料的最大等级 |
| `group_id` | int | 合并组，同组同 id 可合并 |
| `icon` | string | 图标路径，空字符串用默认色块 |
| `describe` | string | 描述文本 |
| `type` | int | ItemType 枚举值 |
| `value` | int | 价值 / 攻击力加成（可选） |
| `sell_price` | int | 出售灵石价格（可选） |

### 发射器字段（type=1 或任意 type 配置后即可生效）

发射能力由 `spawns` + `max_charges` 字段决定，不依赖 `type`。任何类型的物品只要配置了这两项即具备发射器行为。

| 字段 | 类型 | 说明 |
|------|------|------|
| `max_charges` | int | 最大生成次数 |
| `recharge_time` | int | CD 秒数，≤0 时耗尽消失 |
| `spawns` | array | 随机生成表 `[{id, weight}]`，weight 为权重 |
| `fixed_spawns` | int[] | 固定顺序生成（替代 spawns，可选） |
| `no_cost` | bool | true 时不消耗体力/灵力（可选） |

灵石矿脉（`25001–25016`）只产出可使用的 1 级灵石 `1601`，统一为 6 次发射、
12 小时（43200 秒）重置；普通灵矿（`15001–15016`）的三类产出权重统一为：
主矿材 50%、矿芯 25%、玉石 25%。同类产物内部仍按矿口等级保持原有分布。

### 效果字段（type=5 或 type=4 可配置）

效果字段统一维护在 `items.xlsx` 的 `items_effect` 工作表中。`items_recipe_product`
只维护配方产物本体及发射器字段，不再包含 `effect_type`、`effect_value` 两列；导出时
会按 `id` 将 `type=4` 的效果配置合并回对应配方产物。

| 字段 | 类型 | 说明 |
|------|------|------|
| `effect_type` | int | 效果枚举（见下方） |
| `effect_value` | int | 效果数值 |
| `atk` | int | 物品自身攻击力（可选） |

### EffectType 枚举

| 值 | 含义 | effect_value 含义 |
|----|------|-------------------|
| 0 | 无效果 | - |
| 1 | 攻击 | 伤害倍率（剑气） |
| 2 | 治疗 | 恢复 HP 量 |
| 3 | 修为经验 | 增加修为值 |
| 4 | 体力 | 恢复体力值 |
| 5 | 突破 | 突破境界 |
| 6 | 灵力恢复 | 恢复灵力值 |
| 7 | 攻击力加成 | 飞剑等，value=ATK 加成量 |
| 8 | 灵石 | 获得灵石数量 |
| 9 | 卡包（CARD_PACK） | card_collection.packs 中的 pack_id |

### 飞剑（type=4 + effect_type=7）配置示例

飞剑同时是发射器和攻击力加成来源：

```json
{
  "id": 28001,
  "name": "铁木剑",
  "type": 4,
  "value": 1,
  "effect_type": 7,
  "max_charges": 5,
  "recharge_time": 60,
  "spawns": [{"id": 15101, "weight": 100}]
}
```

**机制**：飞剑双击发射剑气（effect_type=1 道具），生成时剑气记录 `atk_base = 境界atk + 飞剑value`。使用剑气攻击时，伤害 = `atk_base × 剑气effect_value`。剑气没有 `atk_base` 时无法造成伤害。

## 4. quests.json — 任务表

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | int | 任务 ID |
| `type` | int | 任务类型（1=合并 2=生成 3=制作 4=出售 5=战斗...） |
| `name` | string | 名称 |
| `description` | string | 描述 |
| `target_count` | int | 目标次数 |
| `rewards` | int/Dict | 奖励配置 ID 或内联奖励 |
| `auto_reward` | bool | 是否自动发放 |
| `reset_cycle` | int | 重置周期 0=不重置 1=每日 2=每周 |

周常任务不奖励经验：每日合成任务奖励 1 个卡包（奖励 ID `3/4/5`，分别为 1/2/3 星）；其余任务奖励 10 体力（奖励 ID `2`，`token=3`）。

周常任务按北京时间每周一 `reset_hour`（当前 05:00）重置进度、完成状态和领取状态；周常页签使用同一时间规则。读取游戏状态、推进任务和领奖时均检查周期，重置先保存再返回；跨年但仍处于同一周时不会重复重置。

## 6. recipes.json — 制作配方表

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | int | 配方 ID |
| `name` | string | 名称 |
| `ingredients` | int[] | 所需材料 item id 列表 |
| `result` | int | 产出 item id |
| `craft_time` | int | 制作时间（秒） |
| `crafting_level` | int | 所需制作等级 |

配方 `ingredients` 只能引用 `type=0` 的普通物品，不能引用配方产物、
发射器或其他非普通物品。同一配方内的材料物品 ID 必须互不相同，
JSON 与 XLSX 双向转换时都会校验材料类型并拒绝重复材料。

全表任意两个配方的材料集合不能存在严格包含关系，即一个配方的全部材料
不能只是另一个配方的部分材料。同一制作台内也不能有材料集合完全相同的
两个配方；不同制作台可以复用相同材料组合。双向转换均会拒绝这些冲突。

制作时间由配方产物等级统一决定：

| 产物等级 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---------|---|---|---|---|---|---|---|---|
| 时间（分钟） | 1 | 3 | 5 | 10 | 20 | 30 | 45 | 60 |

| 产物等级 | 9 | 10 | 11 | 12 | 13 | 14 | 15 | 16 |
|---------|---|----|----|----|----|----|----|----|
| 时间（分钟） | 90 | 120 | 180 | 240 | 360 | 480 | 600 | 720 |

配置生成时会校验所有配方严格使用对应档位，最低 1 分钟，最高 12 小时。

## 7. weekly_tasks.json — 周常任务表

| 字段 | 类型 | 说明 |
|------|------|------|
| `activity_id` | int | 关联的活动 ID（activities.json） |
| `daily_quests` | int[][] | 7 天 × N 个任务 ID |
| `points_per_task` | int | 首次领取任务奖励时获得的积分，当前为 10 |
| `milestones` | array | 阶段列表 `[{stage, required_points, rewards}]`，达到门槛手动领取 |

源表 `weekly_tasks.xlsx` 的 `weekly_tasks` 页按天维护任务与 `points_per_task`（同活动保持一致），`milestones` 页维护 `activity_id/stage/required_points/rewards`，奖励列使用 JSON。
默认 50/100/200/350 积分分别奖励 30 体力、1 个 2 星卡包、60 体力、1 个 3 星卡包。每档每周只能领取一次，不扣积分。任务达标后点击领取任务奖励时计分；自动领奖任务随奖励到账计分，重复事件或重复领奖不再加分。
积分、已计分任务和已领取阶段在北京时间周一 `reset_hour` 与周常任务一并重置。解锁功能时创建零积分状态，不回算历史任务。领奖接口 `POST /api/game/weekly_tasks/claim` 接收 `activity_id/stage/period_key`，先检查本周状态再原子保存奖励与领取标记；跨周旧请求被拒绝。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | int | 活动 ID |
| `name` | string | 名称 |
| `cycle` | int | 周期 0=一次性 1=每日 2=每周 3=每月 |
| `widget` | string | 入口 widget 类名（可选） |
| `start_time` | string | 开始时间 ISO 格式（一次性活动） |
| `end_time` | string | 结束时间 ISO 格式（一次性活动） |
| `enabled` | bool | 可选，显式启停活动；未配置时沿用旧行为 |
| `config` | object | 其他活动可选参数；活动6、7使用独立表，此列留空 |

### 订单补给（OrderSupply，活动 ID 7）

常驻活动，使用 `cycle=0`，不配置开始、结束时间。入口位于棋盘订单列表上方。
专用配置在 `config/xlsx/order_supply.xlsx` 的 `settings` 工作表，导出到 `order_supply.json`。
每行通过 `activity_id=7` 关联活动。`target_count=5` 表示累计 5 次可领取，`reward_count=3` 表示每次奖励 3 个低级合成材料；两项均为正整数。
活动表只维护名称、开关、周期、时间和入口。服务端读取独立表后将参数随活动定义下发，客户端读取方式保持一致。
发射器成功直接生成或合成出当前未完成订单需要的一个物品，或成功开始制作订单直接要求的成品，每次累计 1 次。
制作以配方产物 ID 与订单要求精确匹配，不递归匹配配方材料；制作订单物品的子材料不计数（除非该材料本身也被当前订单直接要求）。
同一次生成或合成即使匹配多个订单也只计 1 次；生成按实际产物匹配，倍数不额外增加次数，重复请求不重复累计。
每个订单物品按要求件数记录已覆盖数量：所需件数已生成、合成或开始制作后，再次完成同类物品不累计。多个订单需要同类物品时按总需求逐件累计，同一动作只覆盖一件。棋盘、制作台、储物袋和暂存区已有的同类成品先抵扣需求，不补发次数。记录随订单保存，领取补给、出售、移动或取出成品不重置；新订单重新记录。
无需凑齐或提交订单，提交订单、投入制作材料、制作完成、取出成品和领奖放入棋盘均不计数。
奖励按当前境界阶段选择基础材料等级：练气前、中、后期分别使用 1、2、3 级；筑基、金丹、元婴分别使用 5–7、9–11、13–15 级。有当前订单时，优先限制为不高于订单实际需要的材料等级：例如练气中期需要 1 级物品时发放 1 级，而不是 2 级；需要更高级物品时仍按境界基础档位补给。制作成品按配方递归拆解为普通材料，各材料分别限制等级，不直接发放制作成品或超出当前阶段的高级材料。没有缺少的物品时按当前订单选材，仍遵守订单材料等级上限；没有可用订单材料时按当前可生成的订单池选材，使用境界等级。多个材料种类轮流发放，直接放入主棋盘空格；空位不足的部分进入物品暂存区。
选材优先按全部未完成订单的数量计算真实材料缺口，扣除棋盘可移动物品、储物道具内物品、储物袋、普通暂存奖励，以及未开始制作台内的材料；正在制作或已完成的成品计入可用数量，其已消耗材料不重复计算。普通材料还会向下拆分合成需求，已有足够低级材料可合成所需材料时不视为缺失。同一库存物品只抵扣一次，已提交订单和突破占位订单不参与计算。仅从有缺口的材料链发放；所有材料足够或全部订单物品已制作完成时，回退到当前订单材料链。
成功领取时，主棋盘全部正在制作的工作台立即变为可取出状态，保留原配方与成品；无额外灵石消耗，不自动取出，也不增加活动次数。未开始制作和已完成的工作台保持原状态。
领取成功后，棋盘补给物品从活动入口依次飞入目标格；每个飞行持续 0.45 秒，物品间隔 0.14 秒，落地后显示棋盘物品。动画期间暂时阻止操作，离开页面时清理动画并恢复操作；进入暂存区的物品不占用棋盘飞行目标。
进度达到目标后停止累计，成功领取后归零重新计数；棋盘完全没有空位时，全部奖励进入暂存区。
进度及领取轮次保存于服务端存档，重新登录后继续累计。

### 爬天梯（StairClimb，活动 ID 6）

专用配置源为 `config/xlsx/stair_climb.xlsx`，导出到 `config/json_output/stair_climb.json`。
`settings` 工作表按 `activity_id=6` 配置组人数、积分倍率和机器人参数；
`rewards` 工作表逐行配置 `activity_id`、`min_rank`、`max_rank`、`stamina`、`spirit_stones`，不再填写整段JSON。
活动名称、开关、入口和起止时间继续维护在 `activities.xlsx`，其 `config` 单元格留空。
本期为北京时间 **2026-10-08 00:00 至 2026-10-11 00:00**，持续 72 小时。

| 独立表参数 | 当前值 | 说明 |
| --- | --- | --- |
| `group_size` | 20 | 每组总人数，真人不足由机器人补齐 |
| `order_points_ratio` | 0.1 | 每价值单位获得的积分，可独立调节 |
| `bot_order_value` | 100 | 机器人每次模拟订单的价值，使用同一积分比例 |
| `bot_min_minutes` / `bot_max_minutes` | 30 / 90 | 每个机器人随机固定的订单间隔（分钟） |
| `rewards` | 11 档 | 每档包含 `min_rank`、`max_rank`、`stamina`、`spirit_stones` |

每单积分为 `max(1, floor(物品总价值 × order_points_ratio))`；价值为零的订单不加分。
物品总价值由服务端按实际交付物品的 `value` 求和，同一物品多件逐件累计，不采用客户端或存档中的订单价值。
例如交付两个价值 116 的物品，总价值 232，本期增加 **23 分**。

第 1 名奖励 300 体力、3000 灵石；第 2～10 名每降一名减少 25 体力、250 灵石，
第 10 名为 75 体力、750 灵石；第 11～20 名统一为 50 体力、500 灵石。
所有数值都可通过 `rewards` 配置。排名按积分降序、达到当前分数的时间升序、入组随机顺序比较。
导表校验活动关联、参数正数与整数约束、机器人时间上下限，以及1–20名奖励无重复无缺漏；服务端启动再次校验并读取独立配置，缺少配置时报错。拆表保留原参数与奖励，不改变活动起止时间。

同境界按入组时的具体 `cultivation.current_level` 匹配（如练气三层）。成员随机选取且分组后固定，突破、重连和服务重启不换组。
机器人从入组开始累计，到截止时间停止。结束后留 30 秒结算缓冲，冻结最终榜单，定时分批给真人自动发奖；离线玩家也会到账，登录可补发。
奖励与领取标记在同一存档提交，避免重复发奖；奖励体力可超过自然恢复上限。参赛者结束后仍可从入口查看结算。

部署 D1 时须先应用 `server/schema.sql`，再部署服务端与客户端。当前服务支持一个爬天梯配置；下一期调整起止时间前须先完成本期全部发奖。


## 9. battle_pass.json — 战令配置

战令等级和奖励只维护在 battle_pass.json；积分倍率与进阶线解锁价格维护在
game_config.json 的 `battle_pass.points_per_value` 和 `battle_pass.premium_unlock_cost`；活动标题与起止时间只维护在
activities.json。activity_id 必须关联活动表；月循环战令使用 `cycle=3`，按中国标准时间
自然月刷新，且不需要配置起止时间。战令积分按活动独立保存，不作为可消耗货币结算；每月刷新时
积分、领取记录和进阶线解锁状态都会重置。

| 字段 | 类型 | 说明 |
|------|------|------|
| passes | array | 战令活动定义，首期仅支持配置一个 |
| activity_id | int | 关联的活动 ID |
| points_token_id | int | tokens.json 中的战令积分 token ID，仅用于显示元数据 |
| tiers | array | 按等级递增的奖励门槛和免费/进阶奖励 |
| level | int | 战令等级 |
| required_points | int | 领取该等级奖励需要的累计积分 |
| free_rewards / premium_rewards | object | 使用现有奖励格式：tokens 数组配置 token 与 amount，items 数组配置 id 与 count |

首期配置暂定为 50 级、每级 10 积分；两条轨道奇数级各奖励 10 体力，偶数级各奖励 1 个 1 星卡包（道具 1701），领取后进入物品暂存区。
订单积分倍率由 `game_config.json` 统一配置为 0.1，进阶线解锁价格统一配置为 500 灵石。
首期战令已启用，按 `cycle=3` 每月循环开放。

## 10. meridians.json — 经脉表

订单候选由当前棋盘上的发射器和制作台计算，固定包含主产物、副产物与配方产物三类。
系统从 `spawns` 与 `recipes` 递归计算真正可制作的订单物品；发射器内产出权重较低
的产物链视为副产物。
随机订单每个物品位置先按 `game_config.orders.recipe_product_probability`
选择配方产物池或普通物品池（含副产物），再在池内按已有来源权重抽取。
当前配方产物概率为 80%，普通物品为 20%。任一池为空或本批已抽完时，
从另一池继续抽取，因此候选不足时整批配方产物占比可能低于 80%。
同一批订单不重复抽取同一物品，固定引导订单与突破订单不使用此概率。
`order_level_ranges` 对应 `meridians.xlsx` 的 `order_level_ranges` 工作表，按
`cultivation.current_level` 配置主产物与配方产物的等级范围；副产物沿用配方产物范围。
固定引导订单直接使用 `fixed_orders`，不经过等级过滤，`order_count` 以 XLSX 为准。
`fixed_orders` 的紧凑形式是“一个对象一波”：`{item_ids:[...]}` 中的每个 ID
对应该波的一个订单，当前波次全部完成后才会显示下一波。XLSX 中可写成每行一波的
`item_ids:{5003,5004,6001}`。需要表达单个订单包含多个物品时，仍可使用旧的嵌套
订单数组与 `item_ids` 配置。
例如：`[{"item_ids":[5003,5004,6001]},{"item_ids":[9003,9004,10001]}]`。
固定订单对象也可提供显式 `rewards`；配置了 `rewards` 时，
服务端直接发放该奖励，不再按订单物品价值进行倍率换算。
普通订单使用奖励 219，订单 `total_value` 按 1:1 转换为灵气；周天灵气消耗按当前订单池最大价值重新标定。

| 字段 | 类型 | 说明 |
|------|------|------|
| `order_level_ranges` | array | 订单等级区间，来源为 `order_level_ranges` 工作表 |
| `thresholds` | array | 阈值列表 `[{stage, count_min, count_max, acupoint_rewards, order_count, fixed_orders}]`；`fixed_orders` 可为 `{item_ids:[...]}` 波次对象数组或旧嵌套订单数组 |

配方产物的 `level` 在导出时按配方依赖树计算，取所需材料的最大等级；循环依赖、缺失配方或无效原料会生成空等级，订单筛选时不会进入有等级限制的候选池。

## 13. home_meridians.json — 家园经脉

设施奖励直接配置在对应阶段的 `circulation_reward.items` 中，完成整个周天时一次发放；
不再维护全局生产奖励表。初始棋盘只保留一个可移动1级灵田发射器 `11001`（3,7），
用于生产首批引导订单的花瓣，其余设施随周天进度发放。
激活穴位只发放 15 点体力，不再发放经验；原穴位经验已并入阶段的 `circulation_reward`，
完成整个周天时统一发放。当前配置共有
556 个周天。凡人两个周天分别发放 1、2 个教程设施，练气一层为 3 个周天，
之后每层练气增加 1 个周天，筑基及以后沿用原周天数量。练气期起每个周天最多发放
2 个非灵石矿设施，可因累计预算已满而减少至1个或0个。发射器与制作台均按累计合成
预算分配奖励数量和等级。凡人第 2 周天另发放 10 灵石。

为平滑前期节奏，凡人和练气期每个周天固定 4 个穴位。凡人每个穴位消耗 5 点灵气，
两轮周天合计消耗 40 点；首阶段六个固定引导订单按 1:1 产出 62 点灵气，保留更多缓冲。
练气期及以后按当前境界订单池的平均订单价值标定：练气一层约需 4 单完成一个周天，
后续随境界逐步提高。目标订单数仅用于离线反推现有 `qi_cost`，不会新增运行时配置字段。
凡人境界总经验为 12，低于练气一层的 48。

设施奖励按境界逐步提高等级：凡人发放 1 级，练气期不超过 4 级，筑基期不超过 8 级，
金丹期不超过 12 级，元婴及以后不超过 16 级。练气期只轮换苗圃、泉眼、药圃、矿口、
炼丹炉和炼器室，并为凡人教程已开放的书架补足4级预算；筑基前期新增兽栏和酒坊，
筑基中期新增灵木园和符桌，筑基后期新增灵潭和阵室并继续提升书架等级。首次开放
的设施从1级开始。周天顺序先发放生产设施，再发放至少已有一个可制作配方的制作台。

除灵石矿外，设施的累计合成目标由 `crafting_reward_budget.py` 的 `FACILITY_MERGE_CHECKPOINTS`
定义：练气九层、筑基后期、金丹后期、元婴后期全部周天完成时，每种已开放发射器与制作台
恰好合成一个4、8、12、16级设施。按 `2^(等级-1)` 折合1级设施数量，累计预算为
8、128、2048、32768；扣除初始棋盘、教程和此前突破奖励后分配差额。练气只有炼丹、
炼器两类，筑基起五类齐全。练气有5种普通发射器（含书架），筑基起8种齐全。
超出预算的奖励位置移除，经验、体力、卡包不变；化神前期不再追加普通设施。
导入、导出和生成配置均校验预算。该预算约束固定进度奖励，不包含商城、活动或
历史存档已经领取的额外设施。
灵石矿保持原配置，不参与上述等级预算：每次突破固定发放1个1级灵石矿 `25001`，
包括元婴突破化神前期。灵石矿合成结果随实际领取数量累积，允许保留不同等级余量。
突破奖励则通过 `cultivation.json` 的
`breakthrough_reward_id` 指向 `rewards.json`；突破消耗物品由 `breakthrough_items` 配置。

制作台的配方依赖会递归解析到发射器族群。配置顺序必须满足：制作台首次发放前，
至少一个配方所需的生产设施已在初始棋盘或更早的周天奖励中开放；同一周天内同时
配置的发射器不视为“已先发放”。后续境界可继续开放该制作台高级配方依赖的生产线。
转换脚本会自动校验这条规则；凡人第二周天的固定炼丹炉奖励继续作为新手引导例外。

| 字段 | 类型 | 说明 |

| `stages` | array | 阶段列表 `[{cultivation_level, name, acupoints, qi_cost, circulation_reward}]` |
| `circulation_reward` | object/number | 整个周天完成时发放的奖励，包含周天经验、体力、灵石和设施 `items`；凡人两个周天分别为1、2件设施，其余为0–2件；每个周天另配置1个4星卡包（1704） |

## 16. card_collection.json — 万象仙册集卡活动

源表为 `config/xlsx/card_collection.xlsx`，包含 `collections`、`card_sets`、`cards`、`packs`、`source_rewards` 五个工作表。活动开关和起止时间仍在 `activities` 表维护，入口 widget 为 `CardCollection`。当前为常驻活动 ID 5、收藏 ID 1。

卡册与开包界面顶部显示活动剩余时间，每秒更新为“天 时:分:秒”。无结束时间显示“长期开放”；开始前显示距开始时间，到期显示“活动已结束”并禁用开包、兑换；时间取服务端下发的活动起止配置，支持UTC及ISO时区偏移。

| 数据段 | 字段与规则 |
| --- | --- |
| collections | collection_id、activity_id、name、duplicate_points_by_star、exchange_pack_id、exchange_cost；不同收藏 ID 的卡片、积分与发奖进度独立 |
| card_sets | set_id、collection_id、name、rewards（JSON，体力 token=3、灵石 token=1） |
| cards | card_id、set_id、name、star（1–5）、icon（可留空，显示文字卡面） |
| packs | pack_id、collection_id、name、star（1–5）、icon、card_count（1–100）、normal_weights（JSON 数组，按 1–5 星顺序） |
| source_rewards | collection_id、source_type（order/circulation）、source_id（留空匹配默认）、min_value、pack_id、count、enabled |

**同星保底：** n 星卡包第一卡位必出一张恰好 n 星卡片，计入 `card_count`。其他卡位按 `normal_weights` 抽星级，同星卡等概率，允许重复。总张数为 1 时仅抽保底槽。所有可抽星级必须有有效卡片，服务端启动时校验。

正式配置：1–5 星卡包分别 2/3/4/5/6 张，其余槽权重均为 `[55,28,12,4,1]`。共 12 个卡组、每组 9 张卡片，按组序分为三个难度段：第 1–4 组简单，最高 3 星；第 5–8 组中等，最高 4 星；第 9–12 组高等，最高 5 星。同一难度段内逐组提高高星卡占比。成功开包后检测完整卡组，自动发放随难度递增的奖励：第 1 组 300 体力/1000 灵石，每组体力递增 100、灵石递增 500，第 12 组为 1400 体力/6500 灵石，无需手动领取。重复卡保留数量，发奖不消耗卡片，每组一次，由永久 `claimed_sets` 标记防止重复发放。

**重复卡积分与兑换：** `collections.duplicate_points_by_star=[1,2,3,4,5]` 表示每张重复的1–5星卡分别获得1/2/3/4/5集卡积分。积分只在成功开包后结算，保留重复卡数量；同一包或全开批次里首次抽到的新卡不计积分，后续重复计积分。每个收藏进度保存可用余额 `duplicate_points`、累计获得 `total_duplicate_points`、兑换次数 `exchange_count`，在首次解锁收藏时初始化为0。

当前 `exchange_pack_id=5`、`exchange_cost=200`，每次扣200积分兑换一个5星卡包（效果道具1705），发送到物品暂存区，仍需手动开启。卡包界面与卡册均展示积分余额、累计获得和兑换按钮；积分不足、活动未开放或有操作尚未确认时禁止兑换。价格、目标包和各星积分均在Excel的collections工作表配置，执行 `1_GenJson.bat` 可导出。

`POST /api/game/card_collection/exchange` 接收 `collection_id`、`request_id`、`expected_exchange_count`；返回 `exchanged=true`、`points_spent`、`pack_id`、最新收藏进度与暂存物品。同一个请求重试只恢复结果；回执淘汰后，旧兑换次数仍阻止重复扣分。余额、卡包、兑换次数和回执一起提交存档，保存失败不留下半结算。

合成本身不直接发放卡包；合成只会推进 `MERGE` 类型任务。仅当任务奖励 `items` 配置了卡包效果道具时才发放，未配置则不发放。手动领奖任务达标后仅变为可领取，点击领取时才发放卡包；自动领奖任务达标时随原奖励发放卡包。不再根据任务目标数量额外赠送卡包。

卡包在 `items.xlsx/items_effect` 配置：`type=5`、`effect_type=9`、`effect_value=pack_id`。道具 ID `1701–1705` 对应 1–5 星卡包（pack_id `1–5`）；每种卡包必须对应唯一效果道具，服务端启动时校验。任务的 `rewards` 指向奖励表，在该奖励行的 `items` 中添加如 `[{"id":1703,"count":1}]` 即奖励一个 3 星卡包。Excel 的 `items(id:count)` 对应填写 `1703:1`。

周常任务每一天的合成任务（1001、1006、1011、1016、1021、1026、1031）分别奖励1、2、3、1、2、3、1星卡包各1个，使用奖励 ID 3/4/5；其余周常任务使用奖励 ID 2，奖励 10 体力。周常任务均不奖励经验，达标后必须手动领取任务奖励，领取成功时同时增加周常积分。

产出规则按达到的最高 `min_value` 档位发放一次；指定 `source_id` 优先于默认规则，指定规则 `enabled=false` 可以禁止该来源发包。

| 来源 | min_value 的含义 | 当前档位（每次一个卡包） |
| --- | --- | --- |
| order | 成功订单的 total_value | 0→1星，200→2星，600→3星 |

订单 `source_id` 默认为0，按最高符合档位发放1包：价值低于200为1星、200–599为2星、600及以上为3星。订单奖励区域仅显示图标和数量，不显示星级文字，提交接口的 `rewards.items` 包含实际卡包奖励。

任务和周天不使用 `source_rewards` 自动赠包。556个周天均在 `home_meridians.circulation_reward.items` 明确配置 `1704:1`，随完成奖励展示和结算，不再额外按周天阶段发3–5星包。任务奖励每周期只领一次，已领取的历史任务不补发。活动停用时暂停订单来源发包、开包和卡组自动发奖，保留存档；显式配置在任务/周天中的卡包仍进入暂存区，待活动开放后开启。

卡包奖励直接进入物品暂存区 `pending_rewards`：每个卡包具有唯一 `uid`，`id` 为效果道具 ID，并携带 `kind="card_pack"`、`collection_id`、`pack_id`、`name`、`icon`。普通奖励省略 `kind` 或使用 `item`。历史暂存卡包保留原 UID 和元数据，因此仍按 `kind` 判断，不依赖旧 `id`。卡包不进入棋盘，不参与物品发现与生产设施解锁。

活动页仅展示卡册及卡组奖励，不展示卡包库存或数量角标。点击暂存区队首卡包进入独立开启界面，支持仅开选中 UID 或一键全开暂存区全部卡包（包括被普通物品隔开的卡包）；普通物品保持原有顺序。每包分别执行同星保底，批量结果按卡片合并展示本次获得数量、新卡标记与持有数量。全开包含停用活动或未知配置卡包时整体拒绝，保留全部物品。

`POST /api/game/card_collection/open` 接收 `collection_id`、`pack_uid`、`open_all`（布尔值）、`request_id`、`expected_opened_count`。选中 UID 是全开的重放保护锚点；每次在副本上计算，卡包消耗、卡片、卡组发奖标记、体力、灵石和回执一起保存成功后才响应。单包和全开均检查所有开放收藏的未发奖完整卡组，合并发放奖励。响应携带 `pending_rewards`、`storage_revision` 和最新收藏进度；有卡组发奖时还包含 `completed_sets`（collection_id、set_id）和 `rewards`，用于显示奖励到账。重试只恢复原结果，不重复发奖。客户端按修订号过滤旧响应。卡包库存只使用 `pending_rewards`；集齐奖励随成功开包自动结算。

仅转换集卡表可运行 `python config/xlsx_to_json.py --only-card-collection`；反向同步可运行 `python config/json_to_xlsx.py --only-card-collection`。常规全量转换也包含此表。

## 验证方式

### 体力自然恢复与离线结算

`stamina.regen_interval=120`、`stamina.regen_amount=1` 表示每两分钟恢复 1 点，自然恢复至 `stamina.max=100` 为止。关闭游戏后仍按服务端存档时间累计，重新登录时补算并保存；未满两分钟的时间保留，满体力时不累积额外恢复，购买或奖励超过上限的余额保留。

顶栏倒计时到期调用 `POST /api/game/stamina/refresh`，服务端保存成功后返回余额与下一次恢复倒计时。客户端不自行发放未保存的体力；断线期间的恢复在重连登录时结算，重复读取不重复发放。

### 顶栏体力与灵力购买

`game_config.xlsx` 中的 `resource_purchase.base_cost`、`resource_purchase.cost_increment`、`resource_purchase.amount` 均为正整数，默认均为 100，导出到 `game_config.json/resource_purchase`。每次购买获得 100 点对应资源；体力与灵力分别计次，价格依次为 100、200、300……灵石。计次按 `reset_hour` 每日重置，当前为北京时间 05:00，重登保留当日次数。付费购买可超过自然恢复上限。

顶栏体力、灵力加号打开购买确认弹窗，灵石加号打开商城。服务端提供报价并校验余额、次数和日期；同一请求重试不重复扣费，保存成功后才更新客户端。修改配置并导出后需重启服务端（Worker 需重新部署）。

### 储物袋容量与解锁费用

在 `game_config.xlsx` 的 `game_config` 工作表中配置以下参数，导出到 `game_config.json/pouch`：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `pouch.initial_slots` | 7 | 新玩家初始可用格数 |
| `pouch.unlock_cost_base` | 100 | 第一次解锁 1 格的灵石费用 |
| `pouch.unlock_cost_increment` | 50 | 每次解锁增加的灵石费用 |

参数均为正整数。第 n 次付费解锁费用为 `unlock_cost_base + (n - 1) * unlock_cost_increment`，默认依次为 100、150、200……灵石；每次增加 1 格。修改配置并重新导出后需重启服务端（Worker 需重新部署）。已解锁容量和付费解锁次数永久保存，取出物品不降低下一次费用。

新玩家创建时保存初始容量和解锁次数，读取存档时不扩容、不回填。满格存入由服务端拒绝，原棋盘物品保留。解锁请求携带 `expected_capacity`，同一容量的重复请求不会重复扣费。

2. 若需要按当前订单池重算订单灵气与周天消耗，先运行 `node config/rebalance_order_qi.mjs`
3. 运行 `python config/xlsx_to_json.py` 重新生成 `json_output/` 下的 JSON

   `python config/expand_home_meridians.py`）
4. 重启服务器 `cd server && npm run dev`
5. 启动 Godot 客户端测试

| --- | --- | --- | --- | --- |

聚宝盆将棋盘上的 1 件低于目标等级的材料拖入顶部图标即使用，飞出同链境界上限材料 ×2；点击图标仍可查看介绍与灵石加次。产物优先放入投料腾出的格子及附近空格，空位不足的部分进入物品暂存区；满盘投料会腾出一格，因此一件落盘、一件暂存。失败恢复原物品，不扣次数。万象炉将棋盘上的 1 件普通物品拖入顶部图标后弹出选择框，只展示同等级、已解锁来源且不同于投料的其他普通物品；确定后一换一，产物飞回投料腾出的棋盘格。没有目标、取消或失败时恢复原物品，不扣次数。材料池仅包含已解锁生产来源的普通材料，排除发射器、制作台、效果道具、固定物品和带实例状态的物品。

`settings.reset_hour=5` 表示北京时间每日 05:00 重置；购买次数当日有效。`rewind_seconds=60` 为太虚时砂回溯窗口。加速与回溯共享次数；加速只推进一个制作台到可领取状态或补满一个等待中的发射器充能，不自动领取产物。回溯覆盖最近一次主棋盘合并、生成、出售，恢复该操作的物品、资源和任务变化；相关状态发生变化或超时则失效，加次与法宝操作也会使旧回溯失效。随机序列、UID 计数、法宝额度和请求回执不回退。

入口位于储物袋左侧，点击显示介绍，再点击“前往使用”选择投料/目标，预览后确认使用；加次单独确认。服务端统一校验版本、日期、报价、解锁和投料实例，按请求 ID 防重，保存失败整笔回滚。超时可以重试原请求，不重复扣费或发奖。

修改表后运行 `config/1_GenJson.bat` 并重启服务端；Worker 需重新部署。首次解锁法宝时建立完整进度，使用次数按正常周期重置。配置往返测试：`python tests/golden_finger_config_smoke.py`（需要 openpyxl）。

| 子表 | 配置用途 |
| --- | --- |

当前常驻六关，世界共 28 行，视口依次为逻辑行 0–7、4–11、8–15、12–19、16–23、20–27，行号越大越靠上。初始固定飞剑在前两关每两行升一级：0–1 行一级、2–3 行二级，依次到 10–11 行六级。从第三关新出现区域（逻辑行 12）开始，预置飞剑统一比原布局降低一级：12–13 行六级、14–15 行七级、16–17 行八级、18–19 行九级、20–27 行十级；导表与服务端均校验向上等级不倒退。底部 3 行已揭雾，只有 3 把一级飞剑可移动，其余飞剑固定；上方内容预置并用迷雾遮挡。逻辑行 3/5/7/9/13 的第 0、5 列分别预置 1/2/3/4/5 级剑气，每级 2 个；新增行 17/21/25 的第 0、5 列各放五级剑气，再于第一关逻辑坐标 (2,5)（第 3 列、从底部第 6 行）增加一份迷雾下的固定五级剑气，替换该格原固定三级飞剑，共 17 个固定剑气，合成后解锁；飞剑合成掉落的剑气仍可移动。怪物实例以坐标区分，同类小怪可重复布置。当前布局仅在首次解锁或正常更换期次时初始化；读取已有秘境不追加区域、不改写格子、不重新开放已通关进度。第一关五级剑气的初始布局修改作用于新创建的秘境存档，已有格子继续沿用存档。

每笔有效订单按完成时的境界发放可移动飞剑至秘境暂存：筑基（修为 11–13）发 1、2 级各三把，金丹（14–16）发 1–3 级各三把，元婴（17–19）发 1–4 级各三把；练气及未指定的化神沿用默认 3 把一级飞剑。境界规则替换默认奖励，突破后下一单立即使用新规则。合成至 2–4 级飞剑时不产生额外物品；合成至 5–6/7–8/9–10/11–12 级时分别掉 1 份 1/2/3/4 级可移动剑气，并分别掉落 1级/1、2级/2、3级/3、4级固定飞剑各一把，每次最多额外掉落两把，合成产物本身不计入上限。等级按合成后的飞剑产物判定，分档互不重叠；导表及服务端加载均按每个产物等级累加全部匹配规则中的飞剑数量，拒绝超过两把的配置。合成掉落仅填当前视口的已揭雾空位，空间不足的部分丢失，不转入暂存。先计算合成消耗释放的源格、产物占格和四邻揭雾，再按 `merge_drops` 配置顺序投放，默认先剑气，再按等级由低到高放固定飞剑。暂存物品作为源不会释放棋盘格。地图推进时回收至暂存的物品统一解除固定，保留原 UID、物品 ID 和等级；重新投放后可移动并作为合成源。棋盘上未离屏的固定物品仍须通过合成解锁。小怪/Boss 奖励空间不足及离屏回收仍进入暂存。

奖励位置以合成产物格或被击败的怪物原格为中心，按直线距离由近到远向外散落；怪物原格释放后也可接收奖励。同距按行、列排序，预览与结算一致，不受存档数组顺序影响。仅投放当前视口内已揭雾且无物品、无怪物的空格，近处放不下继续向外找。Boss 先掉落再推进，只有推进后离屏的奖励随旧物品回收。

GM 面板的“添加秘境飞剑”可指定 1～1000 把、1～12 级飞剑，全部作为可移动物品加入秘境暂存。接口命令为 `add_secret_realm_swords`，数量字段 `amount`、等级字段 `level`；沿用 GM 鉴权。秘境须已解锁，尚未初始化时自动初始化；通关后仍可供给。发放会增加秘境版本、使旧预览失效，并通过回包同步暂存栏。

六关小怪分别需要 4/5/7/8/9/10 级飞剑各一份（第三关起在原需求基础上提高一级）；剑气需求从第三关开始逐关提高一级，六关分别为 3/3/4/5/6/6 级各一份，达到六级后封顶。小怪掉落一级体力和灵石物品各 2 件。六关 Boss 依次需要 7级×1、8级×2、9级×3、10级×4、11级×5、12级×6 飞剑，第一、二关另需六级剑气各 1 份，从第三关开始在原有逐关递增需求上各增加 1 份，第三至六关分别需要 3/4/5/6 份六级剑气，掉落二级体力和灵石物品各 2 件。将当前棋盘已揭雾的可移动飞剑、剑气逐件拖入怪物格提交，每次只消耗拖入的一个实例，按怪物坐标保存 submitted 数量，凑齐全部需求后自动击败、释放格子并掉落实体奖励；未凑齐时不发奖、不推进。怪物尚未提交时数量为零，首次提交时创建记录，部分提交重开后保留。同名小怪分别累计，怪物详情显示已提交数量和持有数量。已移除提交按钮；暂存须先点击放入棋盘再拖入怪物。错误等级、已满需求、固定/隐藏/离屏来源不消耗。挑战 Boss 前须击败当前 6×8 视口内全部小怪，包含迷雾中的小怪与重叠区域遗留小怪；后续离屏小怪不计入。视图返回 remaining_mobs，Boss 详情显示剩余数量，未清完时拒绝拖入提交；服务端返回 mobs_remaining，不扣材料、不发奖、不推进、不变更版本或回执。

每关以 Boss 格为中心的 3×3 九格（含 Boss 本格）为特殊迷雾，使用紫色和“封”字区分；合成四邻揭雾及地图推进揭雾均不能打开封印。击败当前视口内全部小怪后，九格在最后一次小怪结算中同时揭开，保留底层物品实例、固定属性和 Boss；揭雾本身不发奖。特殊范围根据现有 `layout` 中的 Boss 坐标推导，不新增 Excel 列或存档字段，不读取时修复历史进度。导表与服务端要求九格完整位于该关视口、初始有雾、不含其他怪物、不同封印不重叠，并校验所有小怪可从普通迷雾区域到达，避免解锁死循环。

四种物品均可同级二合一，满级不再合成；成功合成会揭示产物上下左右的普通迷雾。体力/灵石物品合成到 2 级后，沿用主棋盘交互，第一次点击选中、再次点击同一物品使用才增加资源：2/3 级体力分别增加 15/45，灵石分别增加 30/90。不设“使用奖励”“收回暂存”按钮，暂存物品需先点击投放至棋盘后使用。击败怪物、首次选中或拖动物品不直接增加资源。体力沿用现有资源增长规则。

怪物上方按 submitted 数量逐件显示飞剑、剑气小图标，按需求顺序排列，每行最多 4 个；保留黑色等级文字，多把飞剑分别显示，不折叠为数量标签。迷雾中的怪物不显示图标，重开秘境按存档恢复。最后一件提交确认后，飞剑和剑气图标汇聚攻击，怪物闪光受击、缩小淡出，随后奖励逐件沿弧线散落并弹入目标格；溢出暂存的奖励飞向暂存栏，Boss 在掉落演出结束后才推进地图。合成掉落的固定飞剑与可移动剑气使用相同散落、落地弹入动画。

动画只播放服务端本次成功结算返回的 effects（request_id、类型、怪物 submitted/defeated、实际发放物品 UID、推进前坐标或 stash 标记）；预览、丢失奖励、预置物品揭雾、普通移动不生成掉落演出。事件随已有防重回执保存，重试返回相同数据，不重复发奖；旧回执缺少事件仍可正常重放。客户端按当前请求 ID 匹配事件并防止重复播放，动画中禁用操作、刷新和分页，确认视图等待演出结束再应用；关闭取消表现 Tween，不取消已确认的结算。服务端需加载本次代码后才能返回攻击和掉落事件，旧服务端仍可显示提交存档图标。

棋盘拖入已有物品的格子时，优先执行同级合成；不能合成且目标可移动时，按主棋盘规则挤开目标。先从目标格按四邻广度优先查找已有空格，同距优先屏幕右、左、下、上，仅接受当前视口内已揭雾且无物品、无怪物的空格；没有已有空格时才与源格交换。同级满级的可移动物品也可挤开，固定目标仅允许同级合成，不可挤开。挤开不揭雾、不升级、不触发掉落，保持物品 UID 与属性。暂存点击投放仍只接受空格。客户端共用 `GridUtils.find_nearest_empty` 与 `BoardDragController.slide` 的 0.15 秒移动动画，服务端共用 `grid_search.ts`；秘境世界行号转换为屏幕坐标后寻空格，保持上下方向优先级一致。

秘境及暂存栏复用主棋盘的棋格贴图与 `GridItem` 展示节点，逻辑棋格 84×84、间距 3，采用统一的 `Constants.BOARD_DISPLAY_SCALE=1.14`。主棋盘和秘境共同使用 `scenes/grid/BoardDragController.gd`：逻辑移动超过 10 像素起拖，真实物品节点跟手，无效落点按 0.2 秒回弹。秘境不再使用独立原生拖拽预览。两者统一调用 `MergeService.can_merge/get_next_item`，秘境注入独立物品链的升级查询，最高级由配置是否存在下一级决定。合成沿用主棋盘的消失/产物弹入效果，表现期间等待服务器确认，失败恢复原存档，服务器快速响应也会保留完整的 0.25 秒产物动效。

主棋盘支持乐观操作队列；秘境为保护合成掉落空间预览与逐件提交，权威请求确认前阻断重复操作。普通空格落点目前直接落位，挤开和交换使用上述共享移动动画。

Boss 击败后地图内容自动下移；每次实际推进后，直接揭开新出现区域最下面一行（推进前 start_row + rows）的全部 6 格迷雾；当前五次推进依次揭开逻辑行 8、12、16、20、24，保留格内物品 UID、等级及固定属性。初始布局及最终 Boss 通关后不额外揭雾。地图无手动拖拽、滚轮或边缘滚动。已揭雾的离屏物品按原 UID、物品 ID 和等级回收，并统一设为可移动，隐藏离屏内容不发放；怪物不会回收或自动结算。暂存区固定显示四格：1、2、3 级飞剑各一格，4 级及以上飞剑与剑气、体力、灵石等其他物品共用第四格。每格显示该组队首一件物品及待投放数量，空组保留淡化空格。各组保持原暂存顺序，固定与可移动物品不另分组；已预留投放的物品立即从组内显示及数量中排除，可交错点击不同组。仅支持点击投放，不能拖入棋盘或直接合成：在同一物品格按下并释放，未超过主棋盘拖拽阈值时，为其预留当前已揭雾且无物品、无怪物、未被其他飞行物品预留的第一个空格，播放独立的 0.35 秒飞入动画，并立即显示该组下一件物品。飞行和请求确认期间可以继续点击暂存，多件同时飞行；place 请求按顺序逐笔使用最新版本提交。满盘（含预留格）提示先合成或使用物品腾出空位，不消耗该组队首物品；投放保留当前 UID 与可移动属性，推进回收物品放入后可正常拖拽、合成。暂存投放队列及飞行动画期间继续锁定棋盘拖拽、使用、收回与刷新；快回包不重复显示落点物品，动画与确认均完成才释放预留。失败清理本地队列并恢复权威显示，不确定的已提交请求通过退出会话、自动登录后重新读取服务器存档确认，不在界面重试；关闭取消未发送项并清理飞行，不取消已发送的服务器结算。棋盘可移动物品仍可拖拽合成。合并预览、合并缩放及合并掉落期间可继续拖动其他未占用物品；当前合并源格、目标格、已知掉落落点及连续操作预留格暂时锁定。期间松手的操作按顺序等待当前请求及表现完成，再以最新版本和原 UID 重新检查合成奖励空间并执行；目标格内容变化则取消该未发送操作，避免误合成。回包重建棋盘按 UID 保留正在跟手的物品与位置；失败及关闭取消未发送操作。怪物战斗动画和地图滚动期间仍不可拖拽。通关后仍能整理、合成和使用剩余物品，订单停止继续发补给。

活动接口为 `GET /api/game/secret_realm`、`POST /api/game/secret_realm/merge_preview` 和 `POST /api/game/secret_realm/action`；操作类型为 `move/place/recall/use/fight`。合成先使用同一份服务端结算代码只读模拟，返回 `free_cells/lost_drops`，不扣物品、不保存、不消耗 UID。无损失直接提交；有损失复用 `ConfirmPopup` 列出名称数量，取消不消耗，确认后提交 `accept_reward_loss=true`。服务端重新校验版本与空间，未确认溢出返回 `merge_reward_overflow`；确认字段纳入防重签名，过期预览不能结算。fight 操作须传棋盘源物品 uid 及怪物 col/row，逐件提交进度与物品扣除同次保存；最后一件另执行掉落与推进。其余请求统一校验期次、版本、实例、迷雾与需求，扣除、掉落、揭雾及推进同次保存。失败不部分扣除；相同请求重放不重复结算。秘境界面不显示刷新或“重试操作”按钮。服务器返回 state_conflict（含秘境预览、结算及其他游戏接口）时，统一取消旧 HTTP 请求与排队操作、清除登录凭证及活动请求缓存，返回登录页自动登录并读取权威存档。秘境已提交结算出现网络、解析或保存失败等不确定结果时也走同一流程。普通物品不足、错误提交等业务拒绝仍只提示；没有待确认结算的预览网络失败可重新拖动。重新登录后存档拉取失败则停留登录页，不使用旧状态离线进入。
