# 多倍体力订单优先产出兼容修复

实测同一灵泉、同一随机晶砂结果、同一4倍体力，使用 `item_ids: [9001]` 时优先生成1级泉水；使用旧格式 `item_id: 9001, count: 1` 时没有识别需求，仍生成3级晶砂。服务端另有 `item_ids: []` 遮盖有效 `items` 的情况。当前配置3303组发射器基础产物与低级需求组合均能触发现有数组格式逻辑，因此不更改正常产出概率。

服务端与客户端均依次读取非空 `item_ids`、非空 `items`、旧格式 `item_id/count`，对象形式保留数量。满足需求后恢复原倍数产出；低级优先仍按实际产物扣费。回归使用真实4级灵泉配置，覆盖随机其他产物链、两件需求、逐次抵扣、体力返还和补齐后恢复4倍，并补充客户端预测回归。

验证结果：多倍体力服务端回归、Godot预测回归、订单补给重复动作回归、Worker编译检查通过。额外运行的 `order_supply_smoke.ts` 在访问未初始化的 `activity_progress[7]` 时失败；内存恢复修复前的订单解析代码后重跑仍在同处失败，确认是已有问题，本次未修改该测试。尚未部署，尚未确定用户实际订单是否属于上述兼容格式。
