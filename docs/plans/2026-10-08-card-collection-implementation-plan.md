# 卡包与集卡活动任务规划

**状态：首版功能已实现并完成本地验证，未部署线上。**

### 本次调整：暂存区开包

- 服务端使用 `pending_rewards` 作为唯一卡包库存，旧计数自动迁移并持久化。
- 独立开启界面支持选中 UID / 全部卡包；跨收藏全开在一个事务内结算，每包独立保底。
- 普通物品保持顺序，满棋盘不影响开包；禁止将卡包领取到棋盘。
- 全局开包回执、选中 UID 与预期开包次数共同防重；保存失败、随机异常或无效包不产生半结算。
- 奖励暂存同步按 storage_revision 忽略乱序旧响应。

### 首版实际交付

- 常驻“万象仙册”，卡包发至物品暂存区，3 组共 15 张卡片。
- 1–5 星卡包分别开出 2/3/4/5/6 张，第一张固定与卡包同星，其余槽权重 `[55,28,12,4,1]`；这些是可调整的初始数值。
- 任务仅通过奖励表中配置的卡包效果道具发放（1701–1705，type=5、effect_type=9）；手动任务领取时结算，自动任务达标时结算。订单价值0/200/600分别发1/2/3星包并在奖励区域展示；每个周天完成奖励配置1个4星包；周常每天一项任务配置1–3星包。具体规则见 `config/CONFIG.md` 第16节。
- 首页活动入口、暂存区开包、卡册、同星保底说明、开包展示与跳过、卡组自动发奖、断线重试和上次结果恢复已接入。
- 集齐奖励为每组 300/500/800 体力和 1000/2000/3000 灵石；成功开包后自动检测并发放，每组一次，保留卡片和重复数量。旧存档已集齐但未发奖的卡组在下一次成功开包时结算。
- 服务端提供操作回执与重复请求校验；D1 使用 JSON 中的独立 `storage_revision` 条件写入，不需要数据库结构迁移。
- 界面采用星级颜色与文字卡面；卡片 icon 配置可替换为正式美术。
- Excel 与 JSON 内容一致，转换脚本已支持此表及单表转换。

验证结果：新增服务端逻辑与接口测试、Godot UI smoke 和实际截图检查通过；相关订单、周天、战令和体力奖励回归通过。`worker:check` 通过；额外严格类型检查与本次修改前对照，均有 32 个已有错误，没有新增错误。`gm_grant_order_items_smoke` 的 `4 !== 7` 失败在修改前代码中同样可复现。

固定随机种子、每种卡包 200 名模拟玩家，仅使用同一种卡包集齐全部 15 张：1 星包中位数 477 包、P90 950 包；3 星包中位数 160 包、P90 344 包；5 星包中位数 26 包、P90 59 包。这是按包数的调试评估，不代表真实游玩天数；低星包独立收集较慢，高星周天奖励用于加快稀有卡收集。

以下保留原始设计与任务拆解，未确定事项已按上述首版配置落地，后续可继续调表。

**目标：** 玩家通过完成任务、提交订单、完成周天获得卡包；开包收集 1–5 星卡片；开包后检测集齐卡组，自动发放大量体力、灵石。

**架构：** 沿用 Godot Control 界面、Excel → JSON 配置和 TypeScript 权威服务端。卡包库存、卡片数量、卡组领奖状态均由服务端持久化；客户端只负责展示和提交操作。

**技术栈：** Godot 4 / GDScript、TypeScript、现有 Worker / 本地服务、D1 存档、Excel 配置导出。

## 一、范围与玩法建议

用户已确定：三类玩法产出卡包、开包收集不同卡片、卡片分 1–5 星、集齐卡组奖励体力和灵石。

已确认的卡包规则：卡包分为 1–5 星五种；n 星卡包每次开启至少获得一张恰好 n 星的卡片。保底为单包生效，不依赖累计开包次数。

| 卡包星级 | 每包必含 |
| --- | --- |
| 1 星 | 至少 1 张 1 星卡片 |
| 2 星 | 至少 1 张 2 星卡片 |
| 3 星 | 至少 1 张 3 星卡片 |
| 4 星 | 至少 1 张 4 星卡片 |
| 5 星 | 至少 1 张 5 星卡片 |

每种卡包的总张数、其余卡位的星级范围与概率、各来源奖励的卡包星级仍待确定。

以下是首版建议，尚不是已确认规则：

| 项目 | 建议方案 | 原因 |
| --- | --- | --- |
| 活动周期 | 首版常驻，不自动清空图鉴 | 优先跑通收集闭环，避免引入赛季结算 |
| 卡包存放 | 物品暂存区，不占棋盘格子 | 避免奖励被满棋盘阻塞 |
| 卡包张数 | 五种卡包分别配置总张数，至少 1 张 | 可独立调整产出，同时确保容纳保底卡位 |
| 卡组规模 | 首版 3 组，每组 5 张，覆盖 1–5 星 | 足够验证稀有度、重复卡和集齐流程 |
| 重复卡 | 保留数量，不消耗已收藏卡 | 首版不扩展兑换经济系统 |
| 集齐奖励 | 成功开包后自动发放，每组一次，不消耗卡片 | 展示奖励目标和已发放状态 |
| 开包方式 | 单包开启，可跳过展示动画 | 先保证操作与状态恢复可靠 |

备选方案：卡包也可作为棋盘可点击物品，但会增加物品配置、领取、背包、消耗与满盘处理；也可做限时赛季集卡，但需要补充到期、未开卡包、未领奖励和跨期存档规则。建议首版采用上表方案。

### 建议产出规则

| 来源 | 发奖节点 | 初始建议 |
| --- | --- | --- |
| 任务 | 手动领取奖励，或自动领奖任务达标结算 | 按任务配置发放指定星级卡包；星级与数量待定 |
| 订单 | 服务端校验并成功消耗订单物品后 | 按订单规则发放指定星级卡包；星级、数量、概率或累计门槛待定 |
| 周天 | 实际完成运转周天的结算节点 | 按周天配置发放指定星级卡包；星级与数量待定 |

- 手动任务达标时不发卡包，点击领取原任务奖励时一起发包；自动领奖任务在达标结算时发包，每周期只发一次。
- 每日、每周任务在新的任务周期重新达标并领奖时可以再次获得卡包；已领取的历史任务不补发。
- 周天对应 `runHomeMeridian`，点亮单个穴位不算完成周天；GM 批量点亮默认不额外发卡包。
- 订单与任务、周天可独立产奖。一个操作同时完成任务时，允许分别获得对应奖励，并展示合计。
- 失败、重放、未开放活动不发奖励；产出数量与原操作一起保存。

### 数值草案（开发前确认，之后可调表）

- 抽卡实现建议：n 星卡包固定 1 个同星保底槽，从恰好 n 星的卡池等权抽取；其余 `card_count - 1` 个槽按该卡包配置抽取。保底槽计入总张数。
- 其余槽位先按配置权重抽星级，再在该星级卡池等权抽卡。五种卡包各自的星级范围和权重待确认，不预设能否开出高于卡包星级的卡片。
- 界面分别说明“必得一张 n 星卡片”和其余卡位概率；其他卡位即使抽中更高星级，也保留同星保底卡。
- 同一包允许出现重复卡，重复卡照常累计；首版不做必出新卡或累计保底。
- 卡组奖励暂拟为每组 `300 / 500 / 800` 体力及 `1000 / 2000 / 3000` 灵石，仅作调试起点。
- 上线前按每日任务数、订单数、周天频率模拟产出与集齐时长，再定正式数值；尤其验证每单一卡包是否过量，以及 5 星是否长期卡住收集。

## 二、玩家流程与界面

1. 完成任务、订单或周天，奖励反馈显示获得的卡包类型和数量。
2. 首页活动区出现“集卡活动”入口，打开后查看卡片收集与卡组奖励。
3. 活动页仅展示总收集进度、卡组及其集齐奖励，不展示卡包数量。
4. 点击物品暂存区的卡包进入独立开启界面，可仅打开当前选中 UID，也可一键全开暂存区卡包。界面提供同星保底、概率、来源和结果；全开保留普通暂存物品。
5. 卡片按星级使用不同边框，同时显示星标、名称和数量；首次获得标记“新”，重复卡标记数量增加。
6. 卡组页中未收集卡显示暗色卡背；成功开包后检测所有开放收藏的未发奖完整卡组并自动结算。
7. 开包结果显示集齐的卡组和体力、灵石到账，刷新顶栏，卡组奖励状态变为“已发放”，无需领奖按钮。

界面要求：

- 复用项目现有仙侠配色与弹窗方式，所有节点使用 Control 系列。
- 卡牌图、卡背、卡包图均从配置读取资源路径；缺失美术时提供可辨识的文字和边框回退，不依赖先完成生图。
- 开包提交中禁用重复点击；超时提供重试与重新同步，不能由客户端猜测结果。
- 服务端已结算后再播放动画；跳过动画、关闭弹窗、切换场景或重连均不影响实际收藏。
- 首版提供活动入口、卡包区、卡组区、开包结果；批量开包、交换卡片、碎片商店和整册大奖不纳入首版。

## 三、配置与存档设计

### 配置

新增 `config/xlsx/card_collection.xlsx` 和导出文件 `config/json_output/card_collection.json`：

| 表 / 数据段 | 主要字段 |
| --- | --- |
| collections | collection_id、activity_id、名称 |
| card_sets | set_id、collection_id、名称、排序、rewards |
| cards | card_id、set_id、名称、star、icon、排序 |
| packs | pack_id、collection_id、名称、star、icon、card_count、normal_weights |
| source_rewards | collection_id、source_type（order/circulation）、source_id（可选）、pack_id、count、enabled；任务奖励不走此表 |

- 活动开关、起止时间继续只在 `activities.xlsx / activities.json` 维护，避免多个配置互相冲突。
- `source_id` 可指定某项任务或周天；订单默认规则也放在配置中。指定规则覆盖默认规则，不叠加重复发奖。
- 卡组奖励复用现有 `RewardConfig` 的体力、灵石 token，不新增货币。
- 保底星级直接使用卡包 `star`，固定至少 1 张同星卡，避免额外字段配置出与卡包星级不符的保底。
- 增加配置校验：ID 唯一、外键存在、卡包与卡片星级为 1–5、总张数为正整数、同星保底卡池非空、卡组非空。总张数大于 1 时，普通槽权重必须有效，正权重对应卡池必须非空；只有 1 张时仅执行同星保底抽取。
- 同步更新 `xlsx_to_json.py`、`json_to_xlsx.py` 和 `config/CONFIG.md`；验证双向转换后 ID、概率、奖励一致。

### 玩家存档

在 `GameState` 增加按 `collection_id` 隔离的数据：

```text
card_collection_progress[collection_id]
  packs: { pack_id: count } # 仅兼容旧存档，读取后迁入 pending_rewards 并清零
  cards: { card_id: count }
  claimed_sets: set_id[]
  opened_count: number
  recent_operations: 有界操作回执（request_id、操作参数、结果）
```

- 旧存档缺少字段时初始化为空；不重置已有任务、战令和经脉进度。
- 收藏唯一数从卡片数量推导，避免两套计数不一致。
- 首版无周期重置；以后新一期使用新的 `collection_id`，不得直接复用并清空旧记录。
- 禁用活动后保留库存与收藏；推荐停止产出、开包和领奖，恢复启用后可继续。若改做限时活动，需先明确到期结算政策。

## 四、实施任务与验收

### 任务 1：配置基础与校验

涉及：新增卡片配置和 Excel；修改活动表、两套转换脚本、`config/CONFIG.md`、`server/src/engine/config_tables.ts`、`server/src/worker/config_data.ts`、`autoload/ConfigDatabase.gd`。

步骤：
1. 确定活动、卡组、卡片、卡包 ID 与产出规则。
2. 建立 3 组样例数据和 1–5 星五种卡包，接入客户端与服务端配置加载。
3. 实现引用、星级、概率、保底校验及转换支持。

验收：转换不丢数据；非法卡池启动时明确报错；活动入口可由配置开关控制。

### 任务 2：收藏领域逻辑

涉及：新增 `server/src/engine/card_collection.ts`；修改 `server/src/storage/interface.ts`、`server/src/engine/game_engine.ts`。

步骤：
1. 实现旧存档初始化、卡包发放、库存读取。
2. 实现服务端抽卡、与卡包星级相同的保底槽、其余随机槽、重复卡计数与新卡标记；允许测试注入随机源。
3. 实现开包后的卡组集齐校验、一次性自动发奖；复用 `applyRewards` 与现有体力溢出规则。
4. 在修改库存前校验活动、卡包、所有抽卡池；避免异常时只扣包不发卡。

验收：空库存不能开包；每包张数准确；分别验证 1–5 星卡包始终含至少一张同星卡，只有 1 张的卡包也满足此规则；其他随机结果不影响保底；重复卡累计正确；未集齐不发奖、已发放不再发；收藏不会被发奖消耗。

### 任务 3：接入三类产出

涉及：`server/src/engine/quest_engine.ts`、`server/src/engine/game_engine.ts`、相关操作响应与客户端奖励展示。

步骤：
1. 在手动任务领取节点或自动任务达标结算节点发放配置的卡包。
2. 在 `completeMeridianAcupoint` 成功结算中发订单卡包，与现有订单去重行为对齐。
3. 在 `runHomeMeridian` 成功结算中发周天卡包。
4. 响应中附带本次新增卡包清单及最新收藏状态，客户端及时刷新数量和提示。

验收：订单与周天来源能通过真实操作获得卡包；任务只有在奖励表配置卡包效果道具时获得；失败不发、重试不重发；一个操作完成多项任务时按各自奖励配置发放；任务重置后可再次获得。

### 任务 4：接口、持久化与重复请求

涉及：`server/src/routes/game.ts`、`server/src/storage/d1.ts`；必要时新增数据库迁移并调整其他存档适配器。

拟定接口：

- `GET /api/game/state`：返回收藏状态及必要的活动配置版本信息。
- `POST /api/game/card_collection/open`：collection_id、pack_uid、open_all、request_id、expected_opened_count；返回合并的卡片结果、最新暂存物品与收藏；有自动发奖时包含 completed_sets 与 rewards，以及最新体力、灵石。
- `POST /api/game/card_collection/claim`：仅保留旧客户端兼容，当前界面不再提供手动领奖入口。

步骤：
1. 严格校验字段类型、ID、活动状态；开包仅接收卡包标识，不接收客户端指定的卡片或星级。
2. 使用同一请求 ID 重试时恢复原回执，不二次抽取或消耗；请求 ID 被不同参数复用时拒绝。
3. 开包计数预期值阻止已清理回执的旧请求再次消耗；自动发奖依赖永久 `claimed_sets` 判重。
4. 在存档副本上计算，库存、卡片、领奖标记、货币、操作回执一起成功保存后才响应成功。
5. 检查部署下的并发保障。现有 `enqueue` 是进程内队列，不能单独保证不同 Worker 实例互斥；若存储层没有保护，增加数据库存储修订号与条件写入，并覆盖所有可能写同一玩家存档的路径。存储修订号与现有玩法 `version` 分开管理，冲突返回可重试错误。

验收：双击、网络重试不会重复扣包或领奖；保存失败不留下半结算；跨实例并发不会覆盖其他游戏操作；成功响应丢失后能恢复同一开包结果。

### 任务 5：客户端同步与活动界面

涉及：`autoload/CloudService.gd`、`autoload/GameState.gd`、`autoload/SaveManager.gd`、`scenes/ui/activity/HomeActivityCard.gd`；新增 `CardCollectionPanel.gd/.tscn`、`CardPackOpeningPopup.gd/.tscn` 及必要的卡片组件。

步骤：
1. 接入请求、成功与失败信号、收藏状态同步、登录与重连恢复。
2. 接入首页卡册入口、暂存区卡包入口；不显示卡包数量和卡组领奖按钮。
3. 完成五种星级卡包的暂存与外观区分、卡组进度、稀有度显示、来源说明、同星保底与其余卡位概率说明。
4. 完成开包结果动画与跳过、新卡 / 重复卡反馈、卡组集齐自动到账反馈。
5. 为请求失败、库存不足、活动关闭、状态冲突提供明确中文提示和恢复操作。

验收：任务产出后物品暂存区立即更新；开包结果与服务端一致；自动发奖后顶栏金额同步；关闭、重开和重登录保持状态；移动端尺寸下滚动、触控与弹窗正常。

## 五、实施顺序与边界

顺序：确认玩法与数值方向 → 配置和状态 → 核心开包 / 领奖逻辑 → 产出与持久化接口 → 客户端界面 → 联调与数值评估。

开发前需确认的主要产品选择：

1. 已确认：卡包奖励发送至物品暂存区，点击后开启当前包或一键全开。
2. 活动常驻还是限时；若限时，结束后的卡包和未领取奖励如何处理。
3. 订单与周天是否每次必得卡包，还是按指定来源、概率或累计次数发放；任务由奖励表明确配置。
4. 卡组数量、重复卡处理、卡组奖励和目标集齐时长。
5. 各星级卡包的总张数、其余卡位星级范围与概率，以及订单、周天分别产出何种星级卡包；任务在奖励表中指定道具 ID。

当前工作区已有活动表、战令逻辑、存档类型和配置文档的未提交变更。实施时应基于最新内容增量接入，不覆盖既有改动。
