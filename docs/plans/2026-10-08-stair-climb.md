# 爬天梯活动实现记录

目标：北京时间 2026-10-08 00:00 至 2026-10-11 00:00，20 人同境界订单积分赛，自动结算体力与灵石。

架构：服务端持久化共享分组，按入组时具体修炼等级匹配，随机抽取未分组玩家，机器人补足。分组不会因突破、重连或服务重启改变。订单与积分同一存档提交；排行榜读取同组真人的权威积分。机器人按入组时间开始增长，到结束时冻结。同分按达到该分数的时间、入组随机顺序排序。

默认数值：每单积分 = max(1, floor(服务器物品表总价值 × order_points_ratio))，比例默认 0.1；第 1 名 300 体力、3000 灵石，第 10 名 75 体力、750 灵石，每档差 25 体力、250 灵石；第 11～20 名各 50 体力、500 灵石。机器人每 30～90 分钟完成一单。均存储在活动配置。

已完成：
1. 增加共享分组与个人积分类型、内存/JSON/D1 存储和 D1 迁移；分组使用版本检查，防止跨 Worker 重复入组。
2. 实现活动服务，接入有效订单、状态加载、排行榜接口。结束后留 30 秒处理已受理订单，再冻结最终榜单；奖励和发奖标记同一存档提交。
3. Worker 每分钟分批自动发奖，本地服务同样定时结算；登录可补发。体力奖励可超过恢复上限。
4. 增加 Control 活动面板、倒计时、排行榜、奖励预览和结算结果；结束后保留已参赛者入口。
5. 更新 JSON、Excel 源表和导表脚本，验证往返转换。
6. 测试真人分组、境界隔离、机器人、截止时间、重复订单、重启/并发及结算幂等；运行 Godot 解析和 UI 冒烟。

部署要求：先执行 D1 migration `0002_stair_climb.sql`，再部署 Worker 与客户端。配置已指定日期，不自动更改为部署当天。当前服务读取一个 StairClimb 活动定义；本期全部发奖结束前，不要替换日期或删除配置。下一期调整日期会使用新的 event_id。


验证结果（2026-10-08）：
- `stair_climb_smoke.ts` 通过：同境随机分组、并发去重、机器人、截止边界、真实物品价值、重复订单、计分后保存失败回滚、离线结算、发奖失败重试、D1/JSON 持久化和并发发奖。
- 卡册接口、战令订单积分/领奖、体力倍率/奖励及 GM 战令积分共 6 项相关回归通过。
- Godot UI 冒烟及活动启停断言通过，排行榜与奖励页已实际渲染检查；修复了积分列自动换行导致竖排的问题。家园与订单界面均有入口。
- Excel 源表与 JSON 一致；在临时目录完整运行两个导表脚本，活动配置往返一致。
- 项目常规 Worker 检查与 `git diff --check` 通过。项目 tsconfig 使用 `noCheck: true`；额外关闭 noCheck 后仍存在原有 game_engine/game/gm 类型错误，新增活动服务与存储代码没有诊断。
- Godot 编辑器解析无新增脚本错误；环境仍有 user 目录/着色器缓存和原有资源 UID 警告。

当前边界：共享分组使用每期单行 JSON，适用于现有规模，较大玩家量需拆分分组表和索引。结算等待 30 秒后冻结存档积分；这不是对任意长时间数据库请求的事务屏障。自动结算每分钟处理 5 名未发奖玩家，玩家登录可即时补发。尚未执行线上 D1 迁移或部署。
